# GitHub Contribution & Engineering Portfolio — Project Atlas

## Objective

GitHub contribution growth is an explicit secondary objective of Project Atlas.

The primary objective remains building a real, reliable and maintainable software project. Contribution activity must emerge naturally from meaningful engineering work — not manufactured to fill a contribution graph.

## Contribution Strategy

Plan and track legitimate contributions through:

- Feature implementation (orchestrator, CLI, MCP servers, CI)
- Bug fixes
- Unit and integration tests
- Test coverage improvements
- Technical documentation (architecture, technology comparisons, setup guides)
- Architecture diagrams and decision records
- Code refactoring
- CI/CD improvements
- Security and reliability improvements
- Code reviews and issue resolution

## Contribution Discipline

These rules are absolute:

- Make commits for logical, independently understandable changes.
- Use descriptive commit messages.
- Never create empty commits simply to increase contribution counts.
- Never rewrite commit history just to manipulate the contribution graph.
- Preserve correct author identity and commit attribution.
- Do not push without the owner's authorization.
- Do not use artificial automation to generate meaningless daily commits.
- Worktree activity alone does not count toward the public contribution graph — only commits pushed to the default branch (or an appropriate `gh-pages` branch) and merged pull requests count.

## Documentation as Engineering Work

Treat documentation as a real deliverable, not optional supplementary material:

- Explain newly implemented modules.
- Document dependencies and their purpose.
- Add architecture diagrams.
- Record technology comparisons.
- Write setup and troubleshooting guides.
- Explain testing strategies.
- Maintain learning guides alongside implementation.

Every code change must include a documentation update in the same commit.

## Portfolio Quality Targets

Ensure the public repository gradually demonstrates:

- A clear README.
- Installation and usage instructions.
- Working examples.
- Architecture documentation.
- Automated tests and coverage reporting.
- CI status.
- Meaningful release history.
- Roadmap and contribution guidelines.
- Transparent known limitations.

Never publish secrets, credentials, private data, unfinished sensitive research, or misleading claims.

## Priority Rule

When selecting work, prioritize changes that simultaneously:

1. Improve Project Atlas.
2. Increase code quality or reliability.
3. Teach the owner a useful engineering concept.
4. Produce a legitimate, reviewable GitHub contribution.

Do not sacrifice software quality or architectural integrity for contribution counts.

## Sustainable Weekly Target (Suggested, Not Required)

- 3–5 days of meaningful coding or testing.
- 1–2 documentation improvements.
- Regular commits grouped by logical changes.
- A weekly review of completed work and unresolved issues.
- Occasional contributions to other open-source projects when relevant (once Atlas is stable).

## Portfolio Expansion

Once Atlas is stable, use it to identify and contribute to other Python, developer-tooling, and AI-agent open-source projects. The target is a GitHub profile that tells a convincing story of consistent engineering growth — not merely a green contribution graph.
